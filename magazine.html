Re-read of the repository on 21 August 2026 · verdict after walking the code, not the README

A newspaper that writes itself once a day, then sits still.

Trendwire is not a chatbot over a firehose. It is a dated magazine issue: ingest what the open web actually discussed in the last twenty-four hours, collapse the duplicates, spend one model call on editorial judgment, and publish a page that does not change until tomorrow. Readers get a headline, a lede, named themes with a “so what,” a people-moves column, and a source-health strip so silence is never mistaken for a quiet day.

The public surface is a Next.js App Router site. The worker is the same process. There is no queue product, no Redis, no object store, no embedding index. Postgres is the ledger, the lock, the archive, and the CMS. That is the whole machine, and after reading it again it is the right size for a once-a-day digest.

The code is already on GitHub at skyspeak/socialproof. This brief is the thing you can take offline: what it is, why the shape is this shape, which vendors I would keep, which I would not bother introducing, and the exact order to turn it on.

01 — The product

Each issue covers a rolling 24-hour window that closes at 13:00 UTC — the Vercel cron time. A backfill for an older date uses the same window math, so yesterday and a week ago are the same shape of job.

Pages never re-fetch Hacker News. They read published rows. Home is cached for five minutes; a dated issue for an hour. That is not a performance flourish. Neon’s free compute is metered in CU-hours, and the cache is how most visitors never wake the database.

The editorial standard is in the system prompt, not in a style guide no one reads: themes are claims, not topic labels; corroboration counts; a quiet day gets fewer themes; people moves must name a real person or they are omitted; confidence is a column — confirmed, reported, chatter — so the UI cannot upgrade a rumor by accident.

There is no email yet. RSS is wired. JSON exists for each date. /api/status is the operational page: unauthenticated, counts only, HTTP 503 when the newest digest failed or Postgres is unreachable, which means an uptime monitor can point at it without parsing.

02 — How a day is assembled

Two HTTP doors call the same function. Vercel Cron, once a day, GET /api/cron/digest. GitHub Actions, every fifteen minutes if you turn it on, POST /api/tick. Both require Authorization: Bearer $CRON_SECRET. Both take a lease, call advance(), and return a report. Neither invokes the other. An earlier design chained chunks over HTTP; Vercel may freeze a function the moment it responds, so an un-awaited fetch can die silently. That pattern is gone on purpose.

Vercel Cron  13:00 UTC     GitHub Actions  every 15 min (optional)
        │                              │
        └──────────► /api/cron/digest  /api/tick ◄──
                            │              │
                            └──────┬───────┘
                                   ▼
                         acquire lease (Postgres)
                         ingest pending sources
                         (batches of 4, ~240s budget)
                         synthesize → publish
                         release lease

advance() does not keep a cursor column. Progress is the run log: whatever run_sources already recorded is, by definition, done. Resume cannot skip a source because some earlier batch failed in the middle of the list. Each invocation is guaranteed to finish at least one batch even if setup already ate the budget — otherwise a slow day livelocks, returning forever having done nothing.

Inside the 300-second Fluid-compute ceiling (Hobby included since April 2025) the pipeline keeps a 240-second internal budget and refuses to start synthesis with less than 45 seconds remaining. A measured full run is about 90 seconds. The resume path exists for slow days and overlaps, not because the happy path cannot fit.

The lock is a lease row, not pg_advisory_lock. Neon’s pooled endpoint is PgBouncer in transaction mode; a session lock taken through it can outlive the logical connection that took it. A row with an expiry is safe under pooling, survives a hard kill (it simply expires), and is inspectable on /api/status.

Four stages

StageWhat actually happens
Ingest Each adapter returns a normalized item list. Adapters never throw into the runner. Outcomes are ok, empty, failed, or skipped, written to run_sources. Upserts are keyed on (source_id, external_id), so re-running a day is idempotent.
Dedup Canonical URL, then content hash of title+body. The richest representative is kept. Duplicate count is retained: being carried by four sources is itself a ranking signal (+25 per extra source in rankScore).
Synthesize Top 60 items, people-tier guaranteed a slice of 15 so a busy AI day cannot crowd them out. One JSON completion. Item indexes mapped back to row ids; invalid enums coerced; empty theme lists treated as failure and fall through to heuristics.
Publish Prior themes and people moves for that digest are replaced. Status flips to published. The page is now a newspaper, not a query.

03 — Seventeen sources

No source is load-bearing. The X tier has three independent paths because mirrors die and Exa needs a key. When those go dark, Techmeme and the newsletters still carry the conversation secondhand, with a few hours’ lag. Degradation is a status chip on the page, not a missing section that looks like a quiet industry.

04 — What lives in Postgres

Eight tables, two migrations, no ORM magic beyond Drizzle. Source rows are seeded from the TypeScript registry on first run so you can disable one in production without a deploy.

TableJob
sourcesRegistry. Unique on slug. enabled is the kill switch.
raw_itemsThe only table that grows. Unique on source + external id. Canonical URL and content hash for cross-source collapse.
digestsOne row per day. Status: pending, ingesting, synthesizing, published, failed.
themes / theme_itemsNamed claims and the items that support them.
people_movesPerson, orgs, role, move type, confidence, evidence.
runs / run_sourcesThe observability half. A broken scraper shows up here instead of shrinking the digest.
locksOne row named digest-pipeline. Holder UUID, expiry. Stealable only when expired.

Two connection strings. The app uses the pooled Neon URL with prepared statements off — required under transaction-mode PgBouncer. Migrations use the direct URL. scripts/migrate.ts prefers DATABASE_URL_UNPOOLED (what the Vercel Marketplace sets) then DIRECT_DATABASE_URL, and warns if you point it at a -pooler host.

Locally there is no server. npm run digest:local applies SQL to PGlite — real Postgres compiled to WASM — then runs the live pipeline. npm test covers the lease (contention, steal-on-expiry, release-on-throw), resume (every source ingested exactly once across 1ms-budget ticks), and synthesis mapping, with no network and no keys.

05 — Would I use any other service?

Re-checked against the code, the platform constraints, and the cost of a rewrite

The short answer: ship on what is already wired. Vercel for the pages, Neon for the ledger, GitHub Actions as the safety net, Anthropic (or OpenAI) for the one daily call, Exa only if you care about first-party X text. I would not introduce Redis, S3, a queue product, Cloudflare Workers, Supabase, PlanetScale, or a VPS in order to turn this on.

Verdict

Keep the current vendors for v1. The one architectural change I would consider later is moving the pipeline off Vercel functions and onto GitHub Actions, so Vercel is only a reader. That is an improvement, not a prerequisite. It is not worth delaying the first published issue.

A once-a-day job that already finishes in about ninety seconds does not need a new cloud. It needs a secret, a schema, and one model key.

Host the pages — keep Vercel

The site is Next.js App Router with time-based revalidation. Vercel is the native host. Cloudflare Pages via OpenNext, Netlify, or Railway would serve the HTML, but you would be buying a port for no product reason. Hobby is enough: the public routes are cheap cached reads.

What Vercel is bad at is being a worker. Hobby cron is once per day and may fire anywhere in the hour; overlapping invocations are not deduped; a handler that returns while work is still in flight can freeze. The codebase already absorbed those facts (lease, tick, no self-fetch, 240s budget). Living with them is cheaper than moving.

Run the pipeline — keep Vercel for now, prefer GitHub Actions later

If I were starting from a blank repo, I would run runToCompletion() inside GitHub Actions against Neon — six-hour jobs, no freeze, no 300-second wall — and let Vercel only render. The tick workflow already exists; today it HTTP-calls Vercel instead of doing the work itself. Flipping that later is a small, clean change.

I would not move the worker to Cloudflare Workers (CPU budget is wrong by an order of magnitude), Inngest or Trigger.dev (a durable-job product for one call a day), Temporal, AWS Lambda plus EventBridge (same serverless shape, more IAM), or a $5 VPS (you then own patching). Fly.io Machines are a respectable alternative if GitHub Actions ever feels cramped. They are not needed to ship.

Database — keep Neon

The schema is ordinary Postgres with unique indexes, a lease row, and versioned SQL. Neon’s pooled plus unpooled pair matches how the code is written. The Vercel Marketplace integration sets both names for you.

Supabase is also Postgres and would work, but you would be paying for Auth, Realtime, and a dashboard this app does not use, and you would lose the one-click Vercel wiring. RDS is an ops job. PlanetScale is MySQL and a rewrite. Turso / libSQL is the wrong concurrency and lock model. SQLite on the function filesystem would vanish between deploys. PGlite stays a local harness, never production.

Model — keep Anthropic, keep the OpenAI failover

One call, ~20k input tokens, 60-item corpus, ~40 seconds in measurement. Sonnet is the right default. OpenAI is already the second provider. I would not add Groq, Gemini, or a local model as a third production path until the first two have actually failed you. The heuristic fallback exists so an outage still publishes something; it is intentionally worse, and the intro says so on the page.

Do not raise SYNTH_MAX_CORPUS without raising LLM_TIMEOUT_MS and measuring. At 120 items a live Sonnet call did not return in ten minutes. On Vercel that is a killed run and a blank day.

X — do not buy the X API

Exa is the only paid source, and it is optional. Mirrors are unreliable by nature. Techmeme is the backstop. Paying for official X access would buy first-party firehose and a ToS maze for a digest that has already decided the open-web reflection is enough. Skip Exa on day one if you want; the X tier still has a pulse.

Reddit — do not change hosts, add OAuth later

The 403 is Reddit blocking unauthenticated JSON from datacenter IPs. Fly, Railway, and AWS see the same wall. Moving the app will not fix it. A Reddit OAuth app will. Until then the source correctly reports skipped instead of lying that the subreddits were quiet.

Things I would not add

ServiceWhy not
Redis / UpstashThe lease is already a row. A second store for one lock is a new failure mode.
S3 / R2Nothing to blob. The archive is rows.
Pinecone / embeddingsClustering is one editorial JSON call, not nearest-neighbor.
Kafka / queuesSeventeen sequential fetches and one completion. A queue would idle 23 hours a day.
Auth (Clerk, NextAuth)The magazine is public. Cron routes are a shared secret. That is the whole security model, and it is the right one.
Email nowRSS works. Resend on publish is the correct later addition, not a launch dependency.

The only services I would consider adding after the first week of published issues: a Reddit OAuth app, Resend if you want the issue in a mailbox, and a free Better Stack or Cronitor check on /api/status. None of those are required to deploy tonight.

06 — Deploying it, in order

Total time is about fifteen minutes if the accounts already exist. You need GitHub (done), Vercel, and Neon. Do not visit the site until step 6. The schema is not there yet, and a missing CRON_SECRET makes both pipeline routes fail closed with 401 — deliberately.

  1. Import the repo in Vercel. Framework preset Next.js, root of skyspeak/socialproof. First deploy is fine. Ignore the empty-state page.
  2. Attach Postgres via the Vercel Marketplace. Storage → Create Database → Neon, Free, a region near you. This sets DATABASE_URL (pooled, runtime) and DATABASE_URL_UNPOOLED (direct, migrations). Prefer this over copying strings from neon.tech by hand.
  3. Set secrets for Production (and Preview if you want preview deploys to work). CRON_SECRET from openssl rand -hex 32. One of ANTHROPIC_API_KEY or OPENAI_API_KEY. NEXT_PUBLIC_SITE_URL as the final origin, no trailing slash. EXA_API_KEY only if you want the two Exa sources live.
  4. Apply the schema from this machine. Copy .env.example to .env, paste the direct connection string, then npm install && npm run db:migrate. If you see errors about SET or prepared statements, you are on the pooler. Stop and use the unpooled host.
  5. Redeploy production so the runtime actually has the env vars. Marketplace variables sometimes attach to a deployment that already started.
  6. Trigger the first run rather than waiting until 13:00 UTC:
    curl -H "Authorization: Bearer $CRON_SECRET" https://YOUR_HOST/api/cron/digest
    A healthy response has outcome: "synthesized", something like 17/17 sources, a theme count, a provider name, and an elapsed time around one to two minutes. out_of_budget is not a failure — call /api/tick or wait for Actions.
  7. Verify. GET /api/status should show database: "connected", llmConfigured: true, latest.status: "published". Then open /, /archive, and /feed.xml.
  8. On Hobby, turn on the tick. GitHub → Settings → Secrets and variables → Actions: SITE_URL (no trailing slash) and the same CRON_SECRET. The workflow in .github/workflows/tick.yml is then a 15-minute resume. It is a no-op once the day is published. It also has a manual date input for backfills. On Vercel Pro you may delete it and cron every few minutes instead; both routes share advance().

07 — Keeping it alive

At this volume the bill is zero, with room. One cron, one model call, a handful of minutes of Neon compute, and — if you enable the tick — about 96 no-op function invocations a day that return in milliseconds once the issue is published.

MeterFree allowanceThis service
Vercel functionsGenerous on Hobby~1 real run + optional tick no-ops
Neon compute100 CU-hours / monthMinutes of active compute per day
Neon storage0.5 GBGrows with raw_items only
LLMYour keyOne call / day, ~20k input tokens

Neon Free suspends compute after five minutes idle. That cannot be turned off on that plan. The first request after a nap pays a reactivation; it is not an error. Page caching exists specifically so most visits never touch Postgres.

If storage approaches the cap, prune. Writes fail until you free space:

DELETE FROM raw_items WHERE fetched_at < now() - interval '90 days';

08 — Honest edges

Reddit from Vercel is dark until OAuth exists. X mirrors die constantly; that is why the tier is a braid, not a single pipe. arXiv is empty on weekends by policy, which is why its lookback is 96 hours and dedup eats the overlap.

The heuristic fallback is genuinely worse. It exists so the service still publishes during an outage, not as a substitute editor. One LLM call a day caps cost and also caps nuance. The corpus is 60 items because 120 did not return in time.

There is no email. Adding Resend at persist-time is small and obvious; it is simply not built. Neon Free will always cold-start. That is a latency tax, not a pager.

Hobby cron is a poor recovery story by itself. If a run dies at 13:01 you wait until tomorrow unless the GitHub tick is on. Turn it on.

How to read this file later

This file is magazine.html at the root of the repository. It has no build step and no network dependency. Double-click it, or from the project directory run open magazine.html on a Mac. To keep a paper or PDF copy: Print, then Save as PDF. The screen bar at the top will not appear on the page.

Local practice, if you want to see a digest before the cloud is wired:

npm install
npm test
npm run digest:local

The last command talks to live sources and, if you have a model key in the environment, will spend one real completion. Without a key it still publishes, via heuristics.
